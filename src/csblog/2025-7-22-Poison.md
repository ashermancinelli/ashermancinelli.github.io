## Combining Repeated Divisors

Debugging this optimization took years off my life:

```admonish quote title="_[[llvm] Don't combine repeated subnormal divisors #149333](https://github.com/llvm/llvm-project/pull/149333)_"
_DAGCombiner performs this rewrite:_
`(a / D; b / D;) -> (recip = 1.0 / D; a * recip; b * recip)`

_However, when D is subnormal, this produces `a*inf` and `b*inf`. With fast-math flags enabled, this creates poisons that break the rewritten consumers. Guard this transformation with checks for subnormal operands._
```

How did this happen?
Why do we need to guard this transformation with checks for subnormal operands?
What is a `poison`?

~~~admonish tip title="_What is 'poison'?_"
`poison` is LLVM's representation for a _value_ produced by _undefined behavior_ or a violation of the compiler's assumptions.

It's a special case of `undef` in the LLVM project's primary intermediate representation (IR).
Any operation that performs an illegal operation may produce a `poison` value (like `INT_MAX + 1` assuming no signed wrapping).
Operations that take poisons as operands may also produce a `poison` value.
They are 'infectious' in this way.

[Read more in the docs here](https://llvm.org/docs/LangRef.html#poison-values).
~~~

In psuedocode, the transformation my PR pertains to is:
```python
# Before
def foo(a, b, c):
    d = a / b
    e = c / b
    return e + d

# After
def foo(a, b, c):
    recip = 1.0 / b
    d = a * recip
    e = c * recip
    return e + d
```

Notice that there is only a single division after the transformation.
Division instructions tend to be more costly than multiplication instructions, so a transformation that turns two divisions into a single division and two multiplications is _usually_ a win.
It might be counterproductive if, say, one of these divisions takes place in an unlikely branch:

```python
# Before
def foo(a, b, c, cond):
    if cond:
        a = a / b
    else:
        b = c / b
    return a + b

# After
def foo(a, b, c, cond):
    recip = 1.0 / b
    if cond: # almost always true
        a = a * recip
    else:    # extremely unlikely
        b = c * recip
    return a + b
```

In the above example, two divisions still just becomes a single division and two multiplications, but because the second division almost never happened in the first place, we _really_ end up with a division _and_ a multiplication where we just had a division before.
Tough tradeoffs.

## Why Was This a Problem?

The reason this was a problem for me, is because the code in question used a _sub-normal_ value for the divisor.

~~~admonish tip title="Subnormal Values"
_Subnormal values_ are a special case of floating-point numbers that are smaller than the smallest _normal_ number, and have a different representation.

```text
0|00000000|00000000000000000000000
^ ^        ^
| |        \ Mantissa/fraction
| \ Exponent 
\ Sign bit
```

~~~

When you combine this with [a common equation for calculating relative error](https://mathworld.wolfram.com/RelativeError.html), you might get into some trouble:

~~~admonish note title="Relative Error"
_Let the true value of a quantity be x and the measured or inferred value x_0. Then the relative error is defined by:_

$$
\delta x = | \frac{x - x_0}{x} |
$$

~~~

Now consider what happens when you calculate the relative error for some calculation, and the expected value is _really_ small - too small for normal the floating-point representation.

Well, on modern hardware and in modern toolchains, it is very common to use the options _DAZ_ and _FTZ_, meaning _Denormals are Zero_ and _Flush To Zero_, often enabled by default when using flags like `-ffast-math`.
When certain hardware instructions encounter subnormal values with a floating-point environment that has _DAZ_ or _FTZ_ enabled, they are converted to zero.
Sometimes these flags can cause [an entire class of bugs related to shared libraries, FTZ and DAZ that we won't even discuss here](https://github.com/llvm/llvm-project/issues/57589).
We won't go into [the dangers of `crtfastmath.o`](https://clang.llvm.org/docs/UsersManual.html#a-note-about-crtfastmath-o) or any of the other dark corners of floating-point semantics either.

These flags enable optimizations that are not "safe" for programs that expect a high level of precision.
One of these such flags is `arcp` which allows division to be treated as a multiplication by a reciprocal
This flag is (unsurprisingly) required for the DAGCombiner transform, since it's rewriting the division into a multiplication by a reciprocal.

## What Were the Actual Transformations?

In our case, consider the relative error calculation function checking two measured values against a subnormal expected value before and after this transformation:

```python
# Before
def relative_error(actual1, actual2, expected):
    error1 = (actual1 - expected) / expected
    error2 = (actual2 - expected) / expected
    return error1 + error2

# After
def relative_error(actual1, actual2, expected):
    recip = 1.0 / expected # This is a problem!
    error1 = actual1 * recip
    error2 = actual2 * recip
    return error1 + error2
```

If, at runtime, the subnormal value were flushed to zero, then the reciprocal would go to infinity, as would the error values.
This would not be entirely unexpected.
However, this is _not_ the behavior we observed.

After this transform, the constant folder was able to further simplify the division into an infinity, because subnormal values are considered to be zero in LLVM's constant folding.
In this test case, we also had the `ninf` fast-math flag enabled, which tells LLVM to assume that no operations can produce an infinity, and if an operation were to produce an infinity, it would be replaced with a `poison` value.

At this point, our error calculation routine goes through these constant folding steps:
```python
# Fold 1.0 / subnormal -> infinity
def relative_error(actual1, actual2, expected):
    recip = infinity
    error1 = actual1 * recip
    error2 = actual2 * recip
    return error1 + error2

# infinity -> poison because of the ninf flag
def relative_error(actual1, actual2, expected):
    recip = poison
    error1 = actual1 * recip
    error2 = actual2 * recip
    return error1 + error2

# Poison * poison -> poison
def relative_error(actual1, actual2, expected):
    error1 = poison
    error2 = poison
    return error1 + error2
```

Our error calculation routine has been completely blown away.
Again, this might not have been problematic; if the relative error calculation resulted in a `poison` and the LLVM backend chose the value `0.0` for `poison`s when lowering this code to assembly, then the program would have only observed an error of `0.0` and thought the calculation produced bit-for-bit identical results.

That's not what happened on all architectures, though.

## Only on Some Architectures?

The actual error we observed was _not_ that the relative error calculation yielded a result of `0.0` after being replaced with a `poison`.
We were instead getting a seemingly random result, but only on some architectures.

This relative error calculation was not checking a single scalar value, but an array of values against an array of expected values.
This checking was vectorized at the LLVM IR level and only one element of the array of expected values was subnormal, so by the time the repeated-divisors transformation in selection-dag was able to combine the two divisions into a single division, only one element of the vector of relative errors was a `poison`.
Every other element of the vector happened to be the same value.

Later on, during instruction selection, I noticed that on the architectures where the test failed, the relative error vector with a `poison`ed lane was being lowered to a broadcast instruction, and on the architectures where the test passed, it was being lowered to a move from static memory.

In the passing case, the value of the vector in static memory had a `0.0` for the first lane (the `poison`) and the other lanes had their respective value.
In the failing case, instruction selection realized that the vector had all identical elements _except for the poison_ and determined that _because a broadcast instruction was available_ it could instead replace the poison with the value of the other lanes so a broadcast instruction could be used.

So, the test only fails when a broadcast instruction is available because the poison is replaced with the value of the other lanes.

[In the LLVM IR, it looked like this:](https://godbolt.org/z/Tvhb1nfMT)
```llvm
define <4 x float> @example_poison_to_broadcast() {
entry:
  ; This vector has mostly 1.0 values with some poison elements
  ; LLVM replaces poison with 1.0 to use a broadcast instruction
  ; if avx2 is enabled.
  %vec = alloca <4 x float>, align 16
  store <4 x float> <float 1.0, float poison, float 1.0, float poison>, ptr %vec, align 16
  %result = load <4 x float>, ptr %vec, align 16
  ret <4 x float> %result
}
```

And then in the assembly _without_ broadcast instructions:
```asm
.LCPI0_0:
        .long   0x3f800000
        .zero   4
        .long   0x3f800000
        .zero   4
example_poison_to_broadcast:
        vmovaps xmm0, xmmword ptr [rip + .LCPI0_0]
        vmovaps xmmword ptr [rsp - 24], xmm0
        vmovaps xmm0, xmmword ptr [rsp - 24]
        ret
```

And _with_ the broadcast instructions:
```asm
.LCPI0_0:
        .long   0x3f800000
example_poison_to_broadcast:
        vbroadcastss    xmm0, dword ptr [rip + .LCPI0_0]
        vmovaps xmmword ptr [rsp - 24], xmm0
        vmovaps xmm0, xmmword ptr [rsp - 24]
        ret
```

Notice how the static value for that _entire vector_ now has the same value so a broadcast can be used?

Poisons can cause all sorts of chaos, and the usual warnings associated with fast-math flags ought to be taken seriously.
