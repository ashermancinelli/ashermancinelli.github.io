```admonish quote title="_[llvm] Don't combine repeated subnormal divisors #149333_"
_DAGCombiner performs this rewrite:_
`(a / D; b / D;) -> (recip = 1.0 / D; a * recip; b * recip)`

_However, when D is subnormal, this produces `a*inf` and `b*inf`. With fast-math flags enabled, this creates poisons that break the rewritten consumers. Guard this transformation with checks for subnormal operands._
```

~~~admonish tip title="_What is 'poison'?_"
`poison` is LLVM's representation for a _value_ produced by _undefined behavior_ or a violation of the compiler's assumptions.

It's a special case of `undef` in the LLVM project's primary intermediate representation (IR).
Any operation that performs an illegal operation may produce a `poison` value (like `INT_MAX + 1` assuming no signed wrapping).
Operations that take poisons as operands may also produce a `poison` value.
They are 'infectious' in this way.

[Read more in the docs here](https://llvm.org/docs/LangRef.html#poison-values).
~~~

In psuedocode, the transformation my PR pertains to is:
```python
# Before
def foo(a, b, c):
    d = a / b
    e = c / b
    return e + d

# After
def foo(a, b, c):
    recip = 1.0 / b
    d = a * recip
    e = c * recip
    return e + d
```

Notice that there is only a single division after the transformation.
Division instructions tend to be more costly than multiplication instructions, so a transformation that turns two divisions into a single division and two multiplications is _usually_ a win.
It might be counterproductive if, say, one of these divisions takes place in an unlikely branch:

```python
# Before
def foo(a, b, c, cond):
    if cond:
        a = a / b
    else:
        b = c / b
    return a + b

# After
def foo(a, b, c, cond):
    recip = 1.0 / b
    if cond: # almost always true
        a = a * recip
    else:    # extremely unlikely
        b = c * recip
    return a + b
```

In the above example, two divisions still just becomes a single division and two multiplications, but because the second division almost never happened in the first place, we _really_ end up with a division _and_ a multiplication where we just had a division before.
Tough tradeoffs.

---

The reason this was a problem for me, is because the code in question used a _sub-normal_ value for the divisor.

```admonish tip title="Subnormal Values"
_Subnormal values_ are a special case of floating-point numbers that are smaller than the smallest _normal_ number, and have a different representation.
```

When you combine this with [a common equation for calculating relative error](https://mathworld.wolfram.com/RelativeError.html), you might get into some trouble:

~~~admonish note title="Relative Error"
_Let the true value of a quantity be x and the measured or inferred value x_0. Then the relative error is defined by:_

$$
\delta x = | \frac{x - x_0}{x} |
$$

~~~

Now consider what happens when you calculate the relative error for some calculation, and the expected value is _really_ small - too small for normal the floating-point representation.

Well, on modern hardware and in modern toolchains, it is very common to use the options _DAZ_ and _FTZ_, meaning _Denormals are Zero_ and _Flush To Zero_, often enabled by default when using flags like `-ffast-math`.
When certain hardware instructions encounter subnormal values with a floating-point environment that has _DAZ_ or _FTZ_ enabled, they are converted to zero.
Sometimes these flags can cause [an entire class of bugs related to shared libraries, FTZ and DAZ that we won't even discuss here](https://github.com/llvm/llvm-project/issues/57589).
We won't go into [the dangers of `crtfastmath.o`](https://clang.llvm.org/docs/UsersManual.html#a-note-about-crtfastmath-o) or any of the other dark corners of floating-point semantics either.
